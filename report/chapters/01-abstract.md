# Abstract

DashCart is the backend of a quick-commerce service that delivers groceries from a nearby dark store within minutes. Customers are matched to a store by pincode, browse its live stock, fill a cart and check out. Checkout reserves the stock, payment goes through Razorpay, and orders left unpaid release their stock after ten minutes.

The project concentrates on a problem that every flash sale exposes: selling more units than a store has when many customers try to buy the last few at the same moment. I implemented five interchangeable stock-reservation strategies behind one interface: a deliberately unsafe read-check-write baseline, optimistic locking, pessimistic locking, a single conditional `UPDATE`, and an atomic Redis Lua script. I compared them with a k6 load test in which 500 buyers try to buy 100 units at once. The baseline sold 500 units, overselling by 400 in every run, while each of the other four sold exactly 100. Taking the stock-row lock as the last step of the checkout transaction ("lock late") cut the median checkout time of the locking strategies by 11–17%; the conditional `UPDATE` was fastest at 340 ms. The same change made optimistic locking 20% slower, and the report explains why. Caching product listings in Redis raised listing throughput from 1,743 to 12,011 requests per second and cut the median response time from 54.9 ms to 6.7 ms.

DashCart is built with Java 21, Spring Boot 4, MySQL, Redis and Kafka, has 76 automated tests with 90% line coverage (39 of them against real database and broker containers), and is packaged with Docker for AWS. The techniques apply to any system that sells a limited resource under contention, such as event tickets, flash sales, seat booking and coupon redemption.

**Keywords:** quick commerce, concurrency control, overselling, optimistic and pessimistic locking, Redis, Kafka, Spring Boot, load testing
